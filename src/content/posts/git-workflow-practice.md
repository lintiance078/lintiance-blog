# Git 工作流的实践与思考：从混乱到有序

最近整理了过去几个项目的 Git 提交历史，发现早期的提交信息简直惨不忍睹——"fix"、"update"、"修改"这样的 commit message 占据了半壁江山。回头看这些提交，完全无法理解当时做了什么改动、为什么要改。

## 为什么要规范 Git 工作流

起初觉得一个人写代码，规范不规范的有什么关系。但实际教训来得很快：

- 一次线上紧急回滚，对着几十条"fix bug"的 commit 无从下手
- 同事接手维护项目，看着分支树一脸茫然
- 合并代码时频繁冲突，因为大家都在往 master 上直接推

好的 Git 工作流不只是为了"好看"，它直接关系到团队的协作效率和代码质量。

## 我现在的实践

### Commit Message 规范

我采用了 Angular 规范的精简版：

```
<type>: <简短描述>

<详细说明（可选）>
```

类型定义：
- `feat`：新功能
- `fix`：Bug 修复
- `refactor`：重构
- `docs`：文档
- `style`：格式调整
- `chore`：构建/工具

### 分支策略

对于个人项目，我采用简化版的 Git Flow：

- `main`：稳定版本，随时可部署
- `develop`：开发主分支
- `feature/xxx`：功能分支，合并到 develop 后删除
- `hotfix/xxx`：紧急修复分支

## 几个实用技巧

**1. 用 `git stash` 暂存工作现场**

正在写功能时突然需要切分支修 bug？`git stash` 是最好的朋友。

**2. `git rebase -i` 整理提交历史**

在合并到主分支之前，用交互式 rebase 把零散的提交压缩成有意义的节点。

**3. 写好 `.gitignore`**

别让 `node_modules`、`.env`、IDE 配置文件污染仓库。推荐使用 gitignore.io 生成模板。

## 写在最后

Git 是一个强大的工具，但工具的价值在于使用方式。花一点时间建立规范，长期来看能节省大量调试和沟通成本。没有银弹式的工作流，关键是找到适合自己团队的节奏。
