# 代码审查的五个实用建议：让 Code Review 不再流于形式

Code Review 是软件开发中最重要的质量保障手段之一，但很多团队的 Code Review 流于形式——要么只是点个"LGTM"（Looks Good To Me），要么变成互相找茬的战场。

## 建议一：Review 的是代码，不是人

这一点说起来简单，做起来难。当别人指出你代码中的问题时，本能反应是防御。但 Code Review 的目标是改进代码质量，不是评判个人能力。

写评论时多用"我们"而不是"你"：
- ❌ "你这里写错了"
- ✅ "这个逻辑可能需要考虑边界情况，比如..."

## 建议二：小 PR 优先

超过 500 行的 PR，Review 质量会显著下降。人的注意力是有限的。

我的做法：
- 单个 PR 控制在 200-400 行
- 一个 PR 只做一件事
- 大的功能拆分成多个小 PR

## 建议三：Review 清单

建立团队的 Review 清单，每次 Review 时逐项检查：

- [ ] 逻辑是否正确？有无边界情况遗漏？
- [ ] 是否有安全风险？（SQL 注入、XSS 等）
- [ ] 错误处理是否完善？
- [ ] 命名是否清晰？变量/函数名是否表达意图？
- [ ] 是否有必要的注释？注释是否解释了"为什么"而不是"是什么"？
- [ ] 测试是否覆盖了关键路径？

## 建议四：区分阻塞性和建议性

不是所有问题都需要修改。把评论分成两类：

- **阻塞性**：必须修改才能合并（逻辑错误、安全漏洞、性能严重问题）
- **建议性**：可以合并，但建议改进（命名优化、代码风格、可读性提升）

建议性评论可以加前缀 `[nit]`（nitpick），表示"小建议，可以不改"。

## 建议五：及时 Review

PR 放久了，上下文就丢失了。提交者忘了当时的思路，Review 者需要重新理解。

团队约定：
- PR 提交后 4 小时内必须有人 Review
- 如果是紧急修复，直接 @ 提醒
- 每天固定时间集中 Review（比如上午 10 点和下午 3 点）

## 最后

Code Review 是一种文化，不是一项任务。当团队成员都认真对待 Review 时，代码质量会显著提升，Bug 会减少，知识也会在团队中自然流动。
