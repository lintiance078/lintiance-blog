## 2. 前置准备：project_local_path.txt

**位置：** 项目根目录下的 `project_local_path.txt`（即 `d:\TRAE开发\lintiance-blog\project_local_path.txt`）

**作用：** 所有一键脚本都通过这个文件找到项目根目录。因为脚本文件夹 `oneclick_scripts` 可能被复制到任意位置，所以需要一个统一的"指路牌"来告诉脚本项目在哪里。

**文件内容：** 只有一行，填写项目的绝对路径。

```
d:\TRAE开发\lintiance-blog
```

**注意事项：**

- 路径中不要包含末尾的 `\`（反斜杠）。
- 路径中不要有中文或空格，否则可能导致脚本执行异常。
- 如果你把项目文件夹移动到了新位置，记得同步更新这个文件。
- 如果文件不存在或内容为空，所有脚本都会报错并退出。

**你是从别处复制的一键脚本包？** 你需要手动创建这个文件，写入你的项目实际路径。

## 3. 安全提醒：配置文件保护

**极其重要：** 所有 `*_config.ini` 文件都包含你的个人 Token，一旦泄露，攻击者可以：
- 操作你的 GitHub 仓库（删除代码、篡改内容）
- 操作你的 Cloudflare 账户（删除站点、修改配置）

**项目已做好的防护：**

`.gitignore` 文件中已经添加了以下规则，确保配置文件不会被提交到 Git：

```
oneclick_scripts/*_config.ini
oneclick_scripts/**/*_config.ini
```

**你需要遵守的规则：**

1. **永远不要**把 `github_config.ini` 或 `cloudflare_config.ini` 的内容发给任何人。
2. **永远不要**把这些文件上传到网盘、聊天群等公开场合。
3. 如果你需要在多台电脑上使用，请在新电脑上重新生成 Token，不要复制配置文件。
4. 定期更换 Token，尤其是在怀疑 Token 可能泄露时。

## 4. 脚本一：项目完整性自检

**文件位置：** `oneclick_scripts\01_一键自检完整性\check_project.bat`

### 4.1 用途

在部署前全面检查项目结构和配置是否完整，帮你发现遗漏的问题。脚本内置 **14 个检查模块**，覆盖目录结构、文件完整性、依赖、配置、组件等各个方面。所有检查结果会自动导出到本地 txt 日志文件（`check_report_YYYYMMDD.txt`），并自动打开供你查看。

### 4.2 检查内容

| 检查类别 | 检查项 | 不及格后果 |
|----------|--------|-----------|
| 目录结构 | `src/pages`、`src/layouts`、`src/components`、`src/styles`、`src/content/posts`、`src/content/hacker-posts`、`public/assets/images`、`functions/api`、`sql` | 缺失目录会导致构建失败 |
| 文章数量 | 普通博客文章 >= 15 篇 | 不足 15 篇为警告，不影响部署 |
| 文章数量 | 黑客博客文章 >= 15 篇 | 不足 15 篇为警告，不影响部署 |
| 关键文件 | `astro.config.mjs`、`package.json`、`wrangler.toml`、`.env` | 缺失会导致无法构建或部署 |
| 环境变量 | `.env` 中 `HACKER_SECRET_KEY` 是否已设置 | 黑客模式无法正常工作 |
| 部署配置 | `wrangler.toml` 中 `HACKER_SECRET_KEY` 是否已配置 | Cloudflare 部署后黑客模式无法使用 |
| 占位符 | `wrangler.toml` 中 `YOUR_D1_DATABASE_ID`、`YOUR_KV_NAMESPACE_ID` 等是否已替换 | 未替换会导致部署失败 |
| 依赖 | `node_modules` 是否存在、`astro` 和 `@astrojs/cloudflare` 是否已安装 | 无法构建和本地开发 |
| Git | `.git` 目录是否存在 | 无法提交代码到 GitHub |
| .gitignore | 是否包含 `.env`、`node_modules`、`oneclick_scripts/*_config.ini` 的忽略规则 | 敏感信息可能被泄露 |
| 文章元数据 | 每篇文章的 frontmatter 是否包含 `title`、`date`、`slug` 字段 | 缺失字段可能导致页面渲染异常 |
| 前端组件 | `HackerMode.astro`、`SettingsPanel.astro`、`SearchBox.astro`、`PostCard.astro`、`BaseLayout.astro`、`global.css`、`[slug].astro`、`index.astro`、标签页、工具函数等 | 缺失组件会导致对应功能不可用 |
| TUI工具 | `tui/index.js` 入口文件是否存在、`blessed` 依赖是否安装 | TUI 工具无法启动 |
| 部署链路 | `.github/workflows` 目录是否存在、Git Remote 是否配置、`wrangler.toml` 是否包含 Pages 构建配置 | 无法自动部署 |
| 一键脚本 | 5 个脚本目录和 7 个 BAT 文件是否完整、`project_local_path.txt` 是否存在 | 对应一键功能不可用 |
| 文档 | `docs` 目录和关键文档文件是否存在 | 缺失文档不影响功能，但影响用户参考 |
| 新增组件 | 侧边栏组件（`Sidebar.astro`）、健康检测组件（`HealthCheck.astro`）、标签隔离（`data-post-type` 属性）、毛玻璃 CSS 变量（`--glass-blur`）、瀑布流 CSS 变量（`--masonry-cols`） | 新增功能不可用或样式异常 |

### 4.3 检查结果

脚本会输出三种状态：

- **[通过]** 绿色标记 — 该项检查合格，无需处理。
- **[警告]** 黄色标记 — 建议修复，但不阻塞部署。
- **[错误]** 红色标记 — 强烈建议在部署前修复，否则可能导致部署失败。

### 4.4 报告文件

所有检查结果均会导出到本地 txt 日志文件，保存在脚本同级目录下。文件名格式为 `check_report_YYYYMMDD.txt`（例如 `check_report_20260805.txt`）。脚本运行完成后会自动打开该报告文件，你也可以在日后随时查阅。

**注意：** 如果报告文件名中包含中文（如 `check_report_周三 20260805.txt`），是因为 Windows 系统的日期格式设置导致的。这不影响使用，但如果你想让文件名更整洁，可以在 Windows 设置中把日期格式改为 `yyyy-MM-dd`。

### 4.5 前提条件

- 无需任何外部工具。
- 无需联网。
- 只需要 `project_local_path.txt` 文件存在且内容正确。

### 4.6 常见问题

**Q: 所有检查都通过了，但部署还是失败？**
A: 自检脚本只检查项目结构和配置文件的完整性，不检查代码逻辑是否正确。请检查 `astro.config.mjs`、`wrangler.toml` 等文件的具体配置是否正确。

**Q: 文章数量警告重要吗？**
A: 文章数量不足只是警告，不会阻止部署。如果你的博客刚搭建好，文章少是正常的，可以忽略这个警告。

## 5. 脚本二：一键提交到 GitHub

**文件位置：** `oneclick_scripts\02_一键提交到GitHub\push_github.bat`

### 5.1 用途

一键完成四个步骤：检查变更 → 添加所有文件 → 提交 → 推送到 GitHub 远程仓库。你不需要打开命令行手动输入 `git add`、`git commit`、`git push` 等命令。

### 5.2 前提条件

- **Git** 已安装（下载地址：https://git-scm.com/download/win）
- 项目已通过 `git init` 初始化，且已关联远程仓库（`git remote add origin <仓库地址>`）
- 有网络连接

### 5.3 配置文件：github_config.ini

**位置：** 与 `push_github.bat` 在同一目录下。

**配置项说明：**

| 配置项 | 含义 | 示例值 | 是否必填 |
|--------|------|--------|----------|
| `GITHUB_REPO_URL` | 你的 GitHub 仓库完整地址 | `https://github.com/username/lintiance-blog` | 是 |
| `GITHUB_TOKEN` | GitHub Personal Access Token（经典版） | `ghp_xxxxxxxxxxxxxxxxxxxx` | 是 |

### 5.4 如何获取 GitHub Token

**步骤（共 9 步）：**

1. 登录 GitHub 网站：https://github.com
2. 点击右上角头像，选择 **Settings**
3. 在左侧菜单栏最下方找到 **Developer settings**
4. 点击 **Personal access tokens** → **Tokens (classic)**
5. 点击右上角 **Generate new token** → **Generate new token (classic)**
6. 在 **Note** 栏填写备注（例如：`一键推送脚本`），方便你日后识别
7. 在 **Expiration** 栏设置过期时间（建议选择 **No expiration**，除非你愿意定期更换）
8. 在 **Select scopes** 中勾选 **repo**（完整的仓库读写权限）。这会给脚本推送代码的权限
9. 点击页面底部的 **Generate token**，然后立刻复制生成的 Token（格式为 `ghp_xxxxxxxxxxxx`）

**重要提醒：**
- Token 离开页面后**无法再次查看**，如果忘记复制，只能删除旧 Token 重新生成。
- 如果不小心泄露了 Token，立即到同一页面删除该 Token，然后生成一个新的。
- 脚本只用 Token 来推送代码，不会做其他事情。

### 5.5 使用流程

1. 双击运行 `push_github.bat`
2. 脚本会显示当前 Git 仓库状态（哪些文件被修改了）
3. 输入提交信息（直接回车则使用默认格式：`Update: 日期 时间`）
4. 脚本自动执行 `git add --all` → `git commit` → `git push`
5. 如果推送成功，显示成功信息；如果失败，显示详细错误原因

### 5.6 限制与风险

| 风险 | 说明 |
|------|------|
| **Token 泄露** | 如果你把 `github_config.ini` 提交到 Git 仓库，任何人拿到 Token 就能操作你的仓库。已通过 `.gitignore` 防护，但你需要确认规则生效。 |
| **--all 误提交** | 脚本使用 `git add --all`，会添加所有变更。如果你有不希望提交的文件（如临时文件、测试数据），请确保 `.gitignore` 已正确配置。 |
| **推送冲突** | 如果远程仓库有你本地没有的新提交，推送会失败。你需要先手动 `git pull` 拉取远程代码，再运行脚本。 |
| **网络问题** | 如果网络不稳定，推送可能超时。重试即可。 |
| **Token 过期** | 如果你设置了过期时间，Token 过期后需要重新生成。 |

### 5.7 常见问题

**Q: 提示"没有检测到任何变更，无需提交"？**
A: 这说明你的本地文件与上次提交完全一致。如果你确认修改了文件，请检查 `.gitignore` 是否把你的文件忽略了。

**Q: 推送失败，提示"远程分支有新的提交，需要先拉取"？**
A: 说明在你上次拉取之后，远程仓库有了新的提交（可能是别人推送的，或者你在另一台电脑上推送的）。打开命令行，在项目目录下执行 `git pull`，解决可能的冲突后，再运行脚本。

**Q: 推送失败，提示 Token 无效（HTTP 401）？**
A: Token 可能已过期或被删除。请重新生成一个新的 Token，替换 `github_config.ini` 中的旧值。

**Q: 推送失败，提示权限不足（HTTP 403）？**
A: Token 生成时没有勾选 `repo` 权限。删除旧 Token，重新生成一个，确保勾选 `repo`。

## 6. 脚本三：一键部署到 Cloudflare Pages

**文件位置：** `oneclick_scripts\03_一键GitHub部署CloudflarePages\deploy_cloudflare.bat`

### 6.1 用途

通过调用 GitHub API 触发 GitHub Actions 工作流，让 Cloudflare Pages 自动从 GitHub 仓库拉取最新代码并部署。这个脚本本身**不做部署**，它只是"按一下按钮"告诉 GitHub Actions 开始干活。

### 6.2 工作原理

```
你运行 deploy_cloudflare.bat
    → 脚本调用 GitHub API（workflow_dispatch）
    → GitHub Actions 启动 deploy.yml 工作流
    → 工作流构建项目并部署到 Cloudflare Pages
    → 部署完成，你的博客更新
```

**前置条件：** 你的 GitHub 仓库中必须已经配置好 `.github/workflows/deploy.yml` 工作流文件，并且 Cloudflare Pages 已经关联了你的 GitHub 仓库。如果还没有配置，请参考 [04-Pages部署教程.md](04-Pages部署教程.md)。

### 6.3 前提条件

- 已配置好 `github_config.ini`（与脚本二共用同一个配置文件）
- 已配置好 `cloudflare_config.ini`
- 项目根目录下存在 `.github/workflows/deploy.yml` 文件
- 有网络连接
- 推荐先安装 `curl`（Windows 10 1803 及以上版本已内置，无需额外安装）

### 6.4 配置文件：cloudflare_config.ini

**位置：** 与 `deploy_cloudflare.bat` 在同一目录下。

**配置项说明：**

| 配置项 | 含义 | 示例值 | 是否必填 |
|--------|------|--------|----------|
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare 账户 ID，32 位十六进制字符串 | `1a2b3c4d5e6f7g8h9i0j1k2l3m4n5o6p` | 是 |
| `CLOUDFLARE_PROJECT_NAME` | Cloudflare Pages 项目的名称 | `lintiance-blog` | 是 |
| `CLOUDFLARE_API_TOKEN` | Cloudflare API Token | `dX4mP...` | 是 |

### 6.5 如何获取 Cloudflare 配置值

#### 获取账户 ID（Account ID）

1. 登录 Cloudflare Dashboard：https://dash.cloudflare.com
2. 在左侧侧边栏中点击 **Workers & Pages**
3. 在页面右侧的边栏中可以看到 **账户 ID** 字样
4. 账户 ID 是一串 32 位的十六进制字符串（如 `1a2b3c4d5e6f7g8h9i0j1k2l3m4n5o6p`）
5. 点击复制按钮，粘贴到配置文件中

#### 获取项目名称

1. 在 Cloudflare Dashboard 中点击左侧 **Workers & Pages**
2. 在 Pages 项目列表中找到你的博客项目
3. 项目名称就是你在创建 Pages 项目时设置的名称（例如 `lintiance-blog`）

#### 获取 API Token

1. 登录 Cloudflare Dashboard：https://dash.cloudflare.com
2. 点击右上角头像 → **My Profile**
3. 在左侧菜单中选择 **API Tokens**
4. 点击 **Create Token** 按钮
5. 找到 **Edit Cloudflare Pages** 模板，点击右侧的 **Use template** 按钮
6. 在 **Account Resources** 中选择你的账户
7. 在 **Zone Resources** 中选择 **All zones**
8. 点击 **Continue to summary** → **Create Token**
9. **立刻复制**生成的 Token，粘贴到配置文件中

**重要提醒：**
- Token 离开页面后**无法再次查看**。如果忘记复制，只能删除旧 Token 重新生成。
- 此 Token 需要 **Cloudflare Pages: Edit** 权限，使用 `Edit Cloudflare Pages` 模板即可自动配置好权限。
- 如果不小心泄露了 Token，立即到同一页面删除该 Token。

### 6.6 使用流程

1. 确保已通过脚本二（`push_github.bat`）将最新代码推送到 GitHub
2. 双击运行 `deploy_cloudflare.bat`
3. 脚本自动验证所有配置 → 调用 GitHub API → 触发部署
4. 如果成功，显示成功信息和部署进度查看链接
5. 你可以打开链接查看 GitHub Actions 的运行状态

### 6.7 HTTP 状态码说明

| 状态码 | 含义 | 建议操作 |
|--------|------|----------|
| 204 | 部署触发成功 | 等待几分钟后访问博客查看效果 |
| 401 | 认证失败，GitHub Token 无效或过期 | 检查 `github_config.ini` 中的 Token，必要时重新生成 |
| 404 | 资源未找到 | 检查仓库是否存在、`deploy.yml` 工作流文件是否存在、Token 是否有该仓库的权限 |
| 422 | 请求无法处理 | 检查 `deploy.yml` 文件语法是否正确，是否配置了 `workflow_dispatch` 触发事件 |

### 6.8 限制与风险

| 风险 | 说明 |
|------|------|
| **Token 泄露** | 本脚本需要两个 Token（GitHub + Cloudflare），泄露任何一个都会造成安全风险。 |
| **无部署状态跟踪** | 脚本只负责触发部署，不会等待部署完成。你需要手动到 GitHub Actions 页面查看部署进度。 |
| **重复触发** | 如果短时间内多次运行脚本，可能会触发多个并行的部署流程，造成资源浪费。通常一次就够了。 |
| **Cloudflare Token 权限** | 如果你使用自定义权限而不是模板，确保 Token 至少有 `Cloudflare Pages: Edit` 权限。 |
| **网络超时** | 如果网络很慢，curl 请求可能超时（默认 30 秒）。重试即可。 |

### 6.9 常见问题

**Q: 部署触发成功，但博客没有更新？**
A: 部署触发成功只表示 GitHub Actions 开始运行了，不代表部署完成。请到 `https://github.com/你的用户名/仓库名/actions` 查看工作流运行状态。如果工作流运行失败，点击查看失败日志。

**Q: 提示"资源未找到 (HTTP 404)"？**
A: 可能的原因：
1. 仓库地址填错了（检查 `GITHUB_REPO_URL`）
2. 项目中没有 `.github/workflows/deploy.yml` 文件
3. Token 没有该仓库的访问权限

**Q: 提示"请求无法处理 (HTTP 422)"？**
A: 你的 `deploy.yml` 工作流文件有问题。请检查：
1. 文件中是否包含 `workflow_dispatch:` 触发器（这是手动触发必须的）
2. 文件语法是否正确（YAML 格式缩进严格）

## 7. 脚本四：本地开发服务

**文件位置：** `oneclick_scripts\04_本地开发服务\start_dev.bat` 和 `stop_dev.bat`

### 7.1 用途

- **`start_dev.bat`**：启动 Astro 本地开发服务器，让您在浏览器中实时预览博客效果。脚本会自动在默认浏览器中打开 **http://localhost:4321**。修改文章或代码后，浏览器会自动刷新。
- **`stop_dev.bat`**：终止占用端口 4321 的 Node/Astro 进程，释放端口以供下次使用。脚本通过 `netstat` 查找监听端口的进程 PID，使用 `taskkill` 强制终止，同时还会扫描并清理残留的 Astro 相关 node 进程。

### 7.2 前提条件

- **Node.js** 已安装（推荐版本 18.x 或更高，下载地址：https://nodejs.org/）
- 项目依赖已安装（`node_modules` 目录存在）。如果不存在，脚本会自动执行 `npm install`

### 7.3 使用流程

**启动：**
1. 双击运行 `start_dev.bat`
2. 脚本检查 Node.js 环境 → 检查依赖 → 启动开发服务器
3. 服务器启动后，脚本会自动在默认浏览器中打开 **http://localhost:4321**
4. 修改 `src/` 下的任何文件，浏览器会自动刷新

**停止：**
1. 双击运行 `stop_dev.bat`
2. 脚本自动查找占用端口 4321 的进程并终止
3. 同时也会检查是否有残留的 Astro 相关 node 进程并清理

### 7.4 关于 localhost:4321

- Astro 开发服务器默认运行在 **4321** 端口（不是常见的 3000 或 8080）。
- 地址为：**http://localhost:4321**
- 如果你需要在同一局域网的其他设备上预览（比如手机），脚本使用了 `--host` 参数，你可以在其他设备上通过 `http://你电脑的IP:4321` 访问。
- 如果你需要修改端口，请在 `astro.config.mjs` 中修改 `server.port` 配置。

### 7.5 限制与风险

| 风险 | 说明 |
|------|------|
| **端口占用** | 如果端口 4321 已被其他程序占用，启动会失败。运行 `stop_dev.bat` 释放端口，或手动关闭占用端口的程序。 |
| **内存占用** | 开发服务器会占用一定的内存（通常 100-300MB）。如果电脑配置较低，编辑大量文章时可能会有卡顿。 |
| **仅限本地** | 开发服务器仅供本地预览，不要把它暴露到公网。它没有安全防护，任何人都可以访问。 |
| **热更新延迟** | 修改某些配置文件（如 `astro.config.mjs`）后可能需要手动重启服务器才能生效。 |
| **npm install 慢** | 如果 `node_modules` 不存在，脚本会自动执行 `npm install`，这可能需要几分钟。如果下载很慢，建议配置 npm 国内镜像源。 |

### 7.6 常见问题

**Q: 启动失败，提示"端口 4321 已被占用"？**
A: 先运行 `stop_dev.bat` 停止旧进程，再重新运行 `start_dev.bat`。如果仍然失败，重启电脑。

**Q: `npm install` 很慢或失败？**
A: 网络问题。可以配置 npm 国内镜像源：
```
npm config set registry https://registry.npmmirror.com
```
然后再运行 `start_dev.bat`。

**Q: 浏览器打开 localhost:4321 显示空白？**
A: 检查终端窗口是否有报错信息。常见原因：`astro.config.mjs` 配置有误，或缺少某些依赖。

**Q: stop_dev.bat 无法终止进程？**
A: 以管理员身份运行 `stop_dev.bat`。右键点击脚本 → 选择"以管理员身份运行"。

## 8. 脚本五：TUI 管理工具

**文件位置：** `oneclick_scripts\05_TUI工具\start_tui.bat` 和 `stop_tui.bat`

### 8.1 用途

TUI（Terminal User Interface，终端用户界面）是一个基于 `blessed` 库的命令行博客管理工具，提供可视化的终端界面，让你在命令行中管理文章、配置站点等。

- **`start_tui.bat`**：启动 TUI 图形化配置管理工具。脚本会自动检查 Node.js 环境、安装依赖（如缺失）、验证 TUI 入口文件，然后在当前终端窗口中启动基于 blessed 的交互式界面。
- **`stop_tui.bat`**：强制结束 TUI 后台进程。脚本通过两种方式查找 TUI 进程：窗口标题筛选（包含 "TUI" 字样）和命令行参数匹配（`tui/index.js`），找到后使用 `taskkill /F` 强制终止。

### 8.2 前提条件

- **Node.js** 已安装（推荐版本 18.x 或更高）
- 项目依赖已安装（`node_modules` 目录存在）。如果不存在，脚本会自动执行 `npm install`
- 项目根目录下存在 `tui/index.js` 入口文件
- 终端窗口尺寸建议至少 **80 列 x 24 行**，否则界面可能显示不正常

### 8.3 使用流程

**启动：**
1. 双击运行 `start_tui.bat`
2. 脚本检查 Node.js 环境 → 检查依赖 → 检查 TUI 入口文件 → 启动 TUI
3. TUI 在当前的命令行窗口中运行，提供可视化的操作界面
4. 使用方向键和回车键进行操作
5. 按 `Ctrl+C` 或 `q` 键正常退出

**停止：**
1. 双击运行 `stop_tui.bat`
2. 脚本通过两种方式查找 TUI 进程：
   - 通过窗口标题查找（包含 "TUI" 字样的窗口）
   - 通过命令行参数查找（包含 `tui/index.js` 的 node 进程）
3. 找到后自动终止

### 8.4 操作说明

TUI 工具的具体操作方法请参考 [02-TUI使用教程.md](02-TUI使用教程.md)。

### 8.5 限制与风险

| 风险 | 说明 |
|------|------|
| **终端尺寸要求** | 终端窗口太小会导致界面元素重叠或显示不全。建议使用 80x24 以上的窗口。 |
| **只能在本机运行** | TUI 是本地命令行工具，无法远程使用。 |
| **强制停止可能丢数据** | 如果使用 `stop_tui.bat` 强制终止（而不是在 TUI 内按 `Ctrl+C` 正常退出），正在编辑但未保存的内容可能会丢失。 |
| **wmic 兼容性** | `stop_tui.bat` 使用 `wmic` 命令查找进程，在最新版本的 Windows 11 中 `wmic` 可能已被弃用，但通常仍可正常使用。如果查找失败，可以手动在任务管理器中结束 node.exe 进程。 |

### 8.6 常见问题

**Q: TUI 界面显示乱码？**
A: 脚本已设置 `chcp 65001`（UTF-8 编码）。如果仍显示乱码，检查终端字体是否支持中文（建议使用 Microsoft YaHei Mono 或 Cascadia Code）。

**Q: TUI 退出后，终端光标不见了？**
A: 这是一个已知问题。TUI 基于 blessed 库，异常退出时可能没有恢复终端状态。关闭当前终端窗口，重新打开即可。

**Q: stop_tui.bat 找不到 TUI 进程？**
A: 可能 TUI 已经正常退出了，或者 TUI 进程的窗口标题/命令行参数与脚本的查找方式不匹配。可以手动在任务管理器中查找 `node.exe` 进程并结束。

**Q: 提示"找不到 TUI 入口文件"？**
A: 确保项目根目录下存在 `tui/index.js` 文件。如果文件被移动或删除，TUI 无法启动。

## 9. 常见问题汇总

### 9.1 所有脚本都报错"找不到项目路径文件"

**原因：** `project_local_path.txt` 文件不存在或内容为空。

**解决：** 在项目根目录下创建 `project_local_path.txt`，写入项目绝对路径（如 `d:\TRAE开发\lintiance-blog`）。

### 9.2 脚本运行后窗口一闪而过

**原因：** Windows 命令行脚本在遇到错误后可能直接退出。

**解决：** 不要双击运行，改为在命令行中运行脚本。打开 cmd 或 PowerShell，`cd` 到脚本所在目录，然后输入脚本文件名运行。这样可以看到完整的错误信息。

### 9.3 脚本中的中文显示为乱码

**原因：** 终端编码不是 UTF-8。

**解决：** 所有脚本开头都有 `chcp 65001` 命令设置 UTF-8 编码。如果仍乱码，可能你的终端字体不支持。在命令行窗口的标题栏右键 → 属性 → 字体 → 选择支持中文的字体。

### 9.4 可以在 macOS 或 Linux 上使用这些脚本吗？

不可以。这些脚本是 `.bat` 格式，只能在 Windows 系统上运行。如果你需要在 macOS 或 Linux 上完成相同的操作，请直接使用对应的命令行命令：
- 自检：手动检查文件和目录
- 提交：`git add --all && git commit -m "信息" && git push`
- 部署：`curl -X POST https://api.github.com/repos/用户名/仓库名/actions/workflows/deploy.yml/dispatches ...`
- 开发：`npm run dev`
- TUI：`node tui/index.js`

### 9.5 脚本运行到一半卡住了？

可能是某个命令在等待网络响应或用户输入。检查终端窗口，看看是否有提示信息。如果长时间无响应，按 `Ctrl+C` 终止，然后重新运行。

### 9.6 如何确认配置文件没有被提交到 Git？

在项目根目录下运行以下命令：
```
git status
```
如果 `github_config.ini` 和 `cloudflare_config.ini` 没有出现在输出中，说明 `.gitignore` 规则生效了。

如果它们出现在输出中，说明规则没生效。请检查：
1. `.gitignore` 文件中是否包含 `oneclick_scripts/*_config.ini` 和 `oneclick_scripts/**/*_config.ini`
2. 规则是否写在文件末尾，且没有多余的引号或空格
